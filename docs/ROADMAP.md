# en-words 未来规划

> 写于 2026-11-10。开始任何一项之前，先读完 [HANDOFF.md](HANDOFF.md)。

## 怎么用这份文档

- 任务按优先级分成四组：**P0** 先做，**P1** 内容，**P2** 功能增强，**P3** 可选的大功能。同一组内按编号顺序做。
- 每个任务写明了：为什么做、具体怎么做、改哪些文件、怎样算完成。照着做，不要自己扩大范围。
- **一次只做一个任务**。做完、验证完、更新完文档，再开始下一个。
- 标了“先问用户”的任务，动手前必须得到用户的明确同意。
- 做完一个任务后，在本文档里把它的状态改成“已完成”并写上日期。

### 每个任务的固定流程

1. 读任务描述和它列出的文件。
2. 在浏览器里看一下库里有没有用户的学习数据（方法见 HANDOFF 第 10.3 节）。有的话，先请用户导出备份。
3. 改代码。纯逻辑写在 `src/srs/`、`src/speaking/`、`src/vocab/` 里，并加单元测试。
4. 运行四条检查命令（HANDOFF 第 0 节），全部通过。
5. 在浏览器里走一遍受影响的流程（HANDOFF 第 10.2 节）。
6. 清掉测试时造的数据。
7. 更新文档：`README.md`（用法变了）、`docs/design.md`（设计变了）、`docs/HANDOFF.md`（规则或坑变了）、本文档（任务状态）。
8. 向用户汇报：做了什么、验证了什么、**没验证什么**。

### 排优先级的依据

用户的目标是面试、同事沟通、技术阅读，要求练习“有效且高效”。判断一件事值不值得做：

- 它能让用户**开口说**得更多、更准吗？能，优先。
- 它能减少用户花在已经会的东西上的时间吗？能，优先。
- 它只是让界面更好看、功能更全吗？靠后。
- 用户还没真正开始用。**在得到真实使用反馈之前，不要做大的新功能**。先做 P0。

### P0-2 给技术词补正确的释义

**状态**：未开始

**状态**：已完成（2026-11-12，待随 v0.3.1 发布）。已建 `content/wordlists/overrides.json`（86 个高频技术词的人工释义，含本文档原来给的 10 个例子），`build-wordlist.mjs` 的 `pack()` 已接入覆盖表并重新生成词典，实测 *scalable* / *serialize* / *stale* / *header* / *cookie* 等显示的都是技术义项；阅读助手点词时优先显示词库同名词条的中文（`app.byTerm` 已导出，词典释义降为次行）。四项检查通过。覆盖表是长期维护项：以后在阅读里再遇到义项不对的词，往 overrides.json 里加一条、重跑生成脚本即可。

**为什么**：词典来自通用词典，部分技术词的释义是日常义项。用户在阅读助手里点 *scalable* 看到“可攀登的”，点 *serialize* 看到“连载”，点 *stale* 第一个义项是“尿”。这会误导。

**怎么做**：

1. 新建 `content/wordlists/overrides.json`，格式是“单词 → 释义”：

   ```json
   {
     "scalable": "a. 可扩展的、可伸缩的",
     "serialize": "vt. 序列化",
     "stale": "a. 过时的、陈旧的（数据）；不新鲜的",
     "stateless": "a. 无状态的",
     "instantiate": "vt. 实例化",
     "throughput": "n. 吞吐量",
     "latency": "n. 延迟",
     "deprecate": "vt. 弃用、不推荐使用",
     "payload": "n. 有效载荷、请求体",
     "polymorphism": "n. 多态"
   }
   ```

2. 找出需要覆盖的词。做法：从 `content/entries/` 里取所有**单个单词**的词条（`kind` 是 `word`），再加上内置内容里出现的技术词，逐个看词典给的释义对不对。先做 100–200 个最常见的，不求一次做完。
3. 修改 `scripts/build-wordlist.mjs`：读 `overrides.json`，生成每个词的释义时，如果这个词在覆盖表里，就用覆盖表的释义。在 `pack` 函数里处理。
4. 重新生成词典：`node scripts/build-wordlist.mjs data/raw/ecdict/ecdict.csv`。
5. 加一个更直接的改进：阅读助手里点一个词时，如果词库里有同名的词条，优先显示词库里的中文。位置在 `src/features/ReadingView.vue` 显示 `selected.word.zh` 的地方，用 `app.byId` 或按 `term` 查找。`stores/app.ts` 里已经有一个 `byTerm` 的 computed（小写英文 → 词条），但没有导出，需要加进 `return` 里。

**涉及文件**：`content/wordlists/overrides.json`（新建）、`scripts/build-wordlist.mjs`、`src/features/ReadingView.vue`、`src/stores/app.ts`。

**怎样算完成**：重新生成后，在阅读助手里点 *scalable*、*serialize*、*stale*，看到的是技术义项。四条检查命令通过。更新 HANDOFF 第 11 节的第 2 条。

### P0-3 测评抽样时过滤掉不合适的词

**状态**：已完成（2026-11-12，待随 v0.3.1 发布）。先做了数据分析再定规则：ECDICT 里纯缩写义项的词条 9236 个、纯地名/英美标注释义的 8825 个，进前 30000 的分别只有 100 个和 11 个。规则已写进 `build-wordlist.mjs` 的读词典循环：所有义项都以 `abbr.` 开头、或都含地名/郡名/国家地区标注的词条不进词典；唯一例外是排名 5000 以内的纯缩写（如 *ceo*，是真词汇）。重新生成后验证：*sussex*、*windsor*、*blackburn* 已不在词典，*ceo* 保留；按完成标准从前 15 段各抽 50 个词（随机种子 42）检查，缩写/地名类零命中。

**为什么**：测评每段只抽 10 个词，抽到一个小写地名（见过 *sussex*）或生僻缩写，这一段的结果就偏了 10%。

**怎么做**：

1. 在 `scripts/build-wordlist.mjs` 读词典的循环里，跳过这些词条（和已有的“男子名、女子名、姓氏”过滤写在一起）：
   - 释义以 `abbr.` 开头的。
   - 释义里含“地名”“（英国）”“（美国）”这类标注、且没有别的义项的。先打印出来看看有多少、是哪些，再决定规则，不要盲目过滤。
2. 在 `src/vocab/assess.ts` 的 `sampleBand` 里已经过滤了长度小于 3 的词，这一条保留。
3. 重新生成词典，跑测试。

**涉及文件**：`scripts/build-wordlist.mjs`。

**怎样算完成**：写一段临时脚本，从前 15 段各抽 50 个词打印出来，人工看一遍，没有地名和缩写。更新 HANDOFF 第 11 节的第 5 条。

### P0-4 阅读助手处理长文

**状态**：已完成（2026-11-12 实测达标，不改代码）。5031 词的文本（一段技术短文重复拼成）在 Node 环境实测：首次 `analyze` 8.3ms，标记一个词后的全文重分析平均 8.8ms、最慢 29.9ms，远低于 1 秒 / 200ms 的阈值，`analyze` 不需要拆分优化。没测到的是浏览器里把上万个片段渲染成 DOM 的帧率；真用几千词粘贴时若有卡顿再回来做分段渲染（原方案第 3 步）。

**为什么**：现在每个词渲染成一个可点击的元素，并且每次标记一个词都会重新分析全文。只用约 150 词的文字测过。用户要读的是书的一节，可能有几千词。

**怎么做**：

1. 先量。准备一段 5000 词左右的英文（可以把一段文字重复多次），粘贴进去，看“分析”要多久、点一个词要多久。
2. 如果分析在 1 秒以内、点词在 200 毫秒以内，**不用改**，记下测量结果就算完成。
3. 如果慢，按这个顺序优化，每做一步重新量：
   - 把“原文切成片段”和“每个片段的状态”分开。切片段（`analyze` 里的正则匹配和词形还原）只在原文变化时做一次；状态在标记变化时重算。需要把 `src/vocab/analyze.ts` 的 `analyze` 拆成两个函数，并更新 `vocab.test.ts`。
   - 原文按段落分块渲染，只渲染当前可见的几段（用 `IntersectionObserver`，做法可以参考 `LibraryView.vue` 里的自动加载）。
4. 超过某个长度（例如 2 万词）时提示用户分段粘贴，不要让页面卡死。

**涉及文件**：`src/vocab/analyze.ts`、`src/vocab/vocab.test.ts`、`src/features/ReadingView.vue`。

**怎样算完成**：5000 词的文字，分析在 1 秒以内，点词收词没有明显卡顿。把测量结果写进 HANDOFF 第 11 节的第 4 条或删掉这一条。

**状态**：已完成（2026-11-12，待随 v0.4.0 发布）。用户要求学单词时要有词源解释（中英双语）、词根词缀、常用用法和场景，一期先落数据现成的两块：

- **构词拆解**：精选词素表 `content/wordlists/morphemes.json`（前缀 48、词根 96、后缀 37，含中文含义和拼写变体），纯逻辑在 `src/lib/morphology.ts`（有单测）：剥前后缀后核心必须命中词根表、或是词典里真实存在的词干（且剥掉的是派生后缀而非屈折后缀）才给拆解，拆不准返回 null 不显示。阅读助手和生词本翻面显示“构词：un-（不）+ pre-（在…之前）+ dict（说）+ -able（能…的）”这类一行。注意口径：这是构词提示，不是学术词源考证，界面和数据文件里都如实标注了。

**状态**：最小版已完成（2026-11-13，随 v0.9.0 发布）。导出备份时把时间记进 `kv` 的 `lastBackupAt`（`app.noteBackupExported`，写失败不挡导出），今日页在“有学习数据且从没备份过、或距上次备份满 7 天（`BACKUP_REMIND_DAYS`）”时显示提醒并直达设置页；`daysSinceBackup` 是纯函数、有单测。File System Access 自动写文件夹那版未做——安卓 App 里用不上文件系统接口，且签名版已能覆盖安装，数据丢失风险主要剩卸载/清数据，最小版提醒已覆盖主要场景，真有需要再说。

**为什么**：数据只在浏览器里，用户清一次浏览器数据就全没了。现在靠用户自己记得导出。

**可以做的**：

- 用浏览器的 File System Access API，让用户选一个文件夹，之后每天自动写一份备份。Edge 和 Chrome 支持。

## P3：可选的大功能

### P3-1 AI 陪练（原方案的 M4）

**状态**：用户选择先不做。**动手前必须先问用户**。

**能带来什么**：

- **自由对话**：现在的场景是固定剧本。接 AI 之后同事的话可以根据用户说的内容变化。
- **口答点评**：现在全靠自评。接 AI 之后可以指出用词不准、语法错误，给出更地道的说法。
- **语音识别**：把用户说的话转成文字，自动判断目标词块有没有用上。

**需要解决的问题**：

1. **API Key**。应用没有后端，Key 放在哪里。两种做法：
   - 写一个很小的本地代理（Node 脚本），Key 放在本机的环境变量里，页面只和本机代理通信。**推荐这个**，Key 不会出现在浏览器里。
   - 页面直接调用 API，Key 存在浏览器里。更简单，但 Key 暴露在浏览器存储中。
2. **费用**。每次对话和点评都要花钱。要让用户能看到用量，并且默认关闭。
3. **隐私**。用户的回答会发到外部服务。要明确告诉用户。
4. **语音识别**。浏览器自带的 `SpeechRecognition`（Chrome、Edge 支持）需要联网，识别带口音的英语不一定准。先单独做一个小实验看准确率，再决定用不用。

**怎么做**（用户同意之后）：

1. 模型用 Anthropic 最新的 Claude 模型。写代码前**先查 Anthropic 的官方文档**确认当前的模型名称、接口和参数，不要凭记忆写。
2. 先只做“口答点评”一个功能，因为它最简单：把题目、提纲、用户回答的文字发给模型，要求返回三样东西：说得好的地方、可以改进的 3 个表达（原话和更好的说法）、漏掉的要点。
3. 用户的回答怎么变成文字：第一版让用户自己打字，或者用浏览器的语音识别。不要一上来就做录音上传转写。
4. 点评里“更好的说法”可以一键加入复习（复用 `app.addChunk`）。
5. 这个功能做成一个独立的模块（例如 `src/ai/`），没有配置 Key 时界面上完全不出现，不影响现有功能。

**怎样算完成**：用户配置 Key 之后，答完一道题能看到点评，并能把其中的表达加入复习。没配置 Key 时应用和现在完全一样。

## 移动端：安卓 App（2026-11-12 用户决定）

用户明确要求把这个项目做成安卓 App。理由和项目目的直接相关：核心练习是开口说，手机随身带麦克风和扬声器，碎片时间也能练。路线选 **Capacitor**：现有 Vue 应用不重写，平台差异只收在 `src/lib/` 的朗读、录音、下载三个文件里。桌面网页版继续保留、行为不变（端口仍是 5310）。

- **阶段 A（验证，进行中）**：最薄的 Capacitor 壳（`@capacitor/core`、`@capacitor/android`、`@capacitor/cli` 均为 8.6，appId `com.asupercat.enwords`，最低 Android 7 / SDK 24，目标 SDK 36），业务代码零改动；安卓清单已加录音权限。APK 用 GitHub Actions 云端打 debug 包（`.github/workflows/android.yml`），不依赖本地安卓环境。**待用户在真机安装后验三件事**：① 学一组后杀掉 App 重开，IndexedDB 数据还在；② 设置页试听和新学朗读有没有声音；③ 口语练习能不能录音并回听（不行就换原生录音插件）。2026-11-12 实测：②确认完全没有声音（WebView 自带 `speechSynthesis` 在安卓上出不了声），已按阶段 B 换成原生 TTS（v0.1.1），待复验；①③待用户反馈。
- **阶段 B（适配）**：按阶段 A 的实测结果给 `tts.ts`、`recorder.ts`、`download.ts` 加原生实现（网页版保持原实现）；移动端样式和触控逐页走查；安卓返回键、安全区。进度：原生 TTS 已完成（v0.1.1，真机确认有声，但系统音色被用户评价“很机械”）；基础适配已完成（v0.2.0：触控目标 44px、触控设备隐藏键盘快捷键提示、状态栏和手势区安全区、窄屏表格和面板收缩、安卓返回键接管为“有历史后退、无历史才退出”）；Azure 神经网络语音已完成（v0.3.0，用户 2026-11-12 选定 Azure 而非 Google）：设置里可选朗读引擎（系统/Azure），Azure 分支在 `src/lib/tts.ts` + 纯逻辑 `src/lib/azure.ts`（SSML、缓存键有单测），合成音频按「句+嗓音+语速」缓存进 IndexedDB 新表 `ttsCache`（DB version 4，上限 300 条删最旧），失败或没填密钥自动回退系统语音；密钥只存本机设置、用户在 App 里自己填。待用户开通 Azure 免费层、填密钥后真机验自然度。剩下：`recorder.ts` 和 `download.ts` 是否需要原生实现，等录音实测和备份导出在 App 内的实测结果；逐页真机走查后修补。

- **阶段 D（移动端专属，用过再说）**：复习提醒通知、自动备份到手机文件夹（对应 P2-5）、听力模式（对应 P2-2）。

## 不建议做的事

下面这些事看起来合理，但和这个项目的定位不符。除非用户明确要求，否则不要做。

- **账号、云同步、多用户**。这是自用工具，数据在本机。
- **做成通用的背单词应用**。它的价值在于内容是为这一个用户的目标定制的。
- **换框架、换构建工具、引入 UI 组件库或 CSS 框架**。现有技术栈够用，换了只有成本。
- **重写或“重构”现有模块**。代码量不大（约 5000 行），结构清楚。没有具体的问题就不要动。
- **给每条内容加更多字段**（词根、同义词、近义词辨析等）。字段多了内容更难写、更难审，对“开口说”帮助不大。
- **游戏化**（积分、徽章、排行榜）。用户是有明确目标的成年人。
- **移动端 App**。（原为“不要做”，2026-11-12 用户明确要求做安卓 App，此条作废，见下面的“移动端：安卓 App”一节。）
- **自己改复习算法**。FSRS 是经过大量数据验证的，不要自己发明间隔规则。可以调参数，见 HANDOFF 第 8.6 节。
